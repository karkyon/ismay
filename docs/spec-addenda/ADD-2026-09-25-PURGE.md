アップロード済みの正本（統合正本v5.0、DOC-09/10/11/12/13）は2026-08-27時点のまま変更していない。本追補は、アカウント削除後30日の物理削除（以下Purge）について、各正本の該当節を**追補・置換**する。

## 1. 対象と範囲

- 対象：`POST /api/v1/auth/account/delete`で`users.deleted_at`を設定されたアカウントの、30日経過後の物理削除。
- 範囲外：個別エンティティのsoft delete（例：Responsibility単体の`deleted_at`）の30日Purge。これは**未実装**（[未決事項台帳](../status/未決事項台帳.md) OPEN-PURGE-04）。

## 2. 統合正本v5.0への追補

### 2.1 §19.3 削除（追補）
- アカウント削除は2段階で行う。soft delete（`deleted_at`設定）の後、30日経過で物理削除する。
- 境界は`deleted_at <= now − 30日`（ちょうど30日で対象）。判定はDB時刻（`now() AT TIME ZONE 'UTC'`）で行う。
- 削除モードの対応は次のとおり。

  | データ | 削除モード |
  |---|---|
  | FKで対象workspace/userへ到達する全表、明示的scope列を持つ表 | `PHYSICALLY_DELETED` |
  | `audit_logs` | `LEGALLY_RETAINED`（本人関係行の`ip_address`は`REDACTED`、`actor_user_id`は`ANONYMIZED`） |
  | Purge台帳3表 | 削除証跡として保持（emailを持たない。object keyはhashのみ） |

### 2.2 §21 API・Transaction（追補）
- Purgeは**1ユーザー1 transaction**で行う。transaction内で次の順に処理する。
  1. `users`行と所属`workspaces`行を`FOR UPDATE`（`lock_timeout`つき）
  2. 30日条件を再検証し、membershipを再取得する
  3. 削除対象行のPKをtemp tableへsnapshotする
  4. Object Storage段（§5.2）
  5. 匿名化・墨消し・循環遮断NULL化・削除
  6. 台帳へ`DB_PURGED`を記録
  7. commit
- 呼出し側から渡されたworkspace ID等は削除の根拠にしない（userIdのみ）。

### 2.3 §22.1 必須制約（追補）
- workspace/userへFKで到達しない表は、**明示的scope列**（`workspace_id → workspaces`）を持つか、保持理由を`PURGE_RETENTION_POLICY`へ登録することを必須とする。どちらでもない表が存在すると、Purgeは実行を拒否する。

## 3. DOC-09 Consent・DataGovernanceへの追補

| 節 | 追補内容 |

## 5. DOC-11 API・Event仕様書への追補

### 5.1 HTTP
| API | 状態 |
|---|---|
| `POST /api/v1/admin/purge/dry-run` | **fail closed**。認証・CSRFの確認後、常に`403 ACCESS_DENIED`を返し、試行を`audit_logs`へFAILUREとして記録する。全テナント横断の操作を許可するPlatform Admin契約が正本で確定するまで再開しない |
| `POST /api/v1/admin/purge/execute` | 同上 |

Workspaceの`OWNER/ADMIN`は、全テナントの管理者として扱わない。

### 5.2 運用CLI契約（`scripts/run_account_purge.ts`）
| 引数 | 動作 |
|---|---|
| （なし） / `--email=` / `--all` | dry-run（transaction内で計画してrollback。Object Storageの見込み件数も表示） |
| `--execute` | 確認文字列「物理削除」の入力後、新しいrunを作成して処理する |
| `--resume=<runId>` | 未完了itemの再開（期限切れleaseの再取得、backoff期限を過ぎたretry） |
| `--status=<runId>` | 台帳の表示 |
| `--batch-size=<n>` / `--max-attempts=<n>` | 1回あたりの処理件数 / dead-letterまでの試行上限 |

exit codeはbitmaskで、`0`＝全完了、`1`＝致命的エラー、`2`＝未完了itemあり、`4`＝監査記録未完了。

### 5.3 Object Storage段の順序（DEC-PURGE-02B §7.1）
1. DB参照key（`OBJECT_KEY_COLUMNS`）と`{workspaceId}/`接頭辞一覧の和集合を台帳へsnapshot
2. MinIO objectを削除
3. statObjectのNotFoundと接頭辞一覧が空であることで不存在を確認（確認できなければDBへ進まずretry）
4. DB物理削除（台帳の`DB_PURGED`と原子的に記録）
5. 監査記録（`audit_logs`、actorType=SYSTEM）
6. commit後の遅延objectを再回収し、object keyを墨消しして完了
